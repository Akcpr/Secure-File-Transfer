Security Layers
1
Transport Security — TLS/SSL
All socket traffic is wrapped in TLS using a self-signed certificate. The client verifies the certificate before connecting, preventing man-in-the-middle attacks on the local network.
TLS / SSL
2
File Confidentiality — AES-256-GCM
Every file is encrypted with a freshly generated AES-256 key and a random 12-byte IV before leaving the client. AES-GCM is an authenticated mode — it detects any tampering of the ciphertext.
AES-256-GCM
3
Key Transport — RSA-2048-OAEP
The AES key is encrypted with the client's RSA-2048 public key using OAEP padding before being sent to the server. Only the client holding the matching private key can recover the AES key on download.
RSA-2048-OAEP
4
File Integrity — SHA-256
A SHA-256 hash of the original plaintext is computed before upload and stored with the metadata. After decryption on download, the hash is recomputed and compared — any corruption or tampering causes the file to be rejected.
SHA-256
5
Password Protection — Salt + Pepper + Hash
Passwords are hashed client-side using SHA-256 with a per-user salt (derived from the username) and a server-wide pepper (from the PASSWORD_PEPPER env var). The plaintext password never leaves the client.
SHA-256 + salt + pepper
6
Session Management — UUID Tokens
After login, a UUID session token is issued and tied to the socket file descriptor. Every command is validated against the session before execution. Sessions expire after 24 hours and are deleted on disconnect.
UUID · 24h expiry
Note on password hashing: The current implementation uses SHA-256, which is fast and not ideal for password storage. argon2-cffi is listed in requirements.txt and is the recommended replacement for a production deployment — it is memory-hard and resistant to brute-force and GPU-based attacks.
